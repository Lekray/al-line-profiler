# Досье безопасности

Документ для службы безопасности, которая решает, можно ли ставить этот инструмент на
сервер приложений Microsoft Dynamics NAV. Ниже описано, что именно инструмент делает на
сервере, какие права ему нужны, какие данные он видит и как всё это проверить по
исходникам самостоятельно. Знание NAV не предполагается — специфика объясняется по ходу.

Каждое утверждение здесь либо снабжено ссылкой на код или командой для проверки, либо
не написано вовсе.

## 1. Что это и что ставится

AL Line Profiler — построчный профайлер серверного кода NAV: листинг объекта с
длительностью каждой строки, числом выполнений и запросами SQL, которые эта строка
породила. Ставятся две вещи:

| Что | Куда | Из чего |
|---|---|---|
| 17 объектов NAV (Table/Page/Report/Codeunit, номера 110200–110207) | в базу данных NAV, штатным импортом | текстовый экспорт `LineProfiler.txt` (читается глазами, ~530 КБ) |
| Сборка .NET `AlLineProfiler.dll` — приёмник событий трассировки | `Service\Add-ins\LineProfiler\` под корнем платформы NAV | один исходный файл `src/AlLineProfiler.cs`, ~1600 строк C# |

Второй файл в папке надстройки — `Microsoft.Diagnostics.Tracing.TraceEvent.dll` — **не
наш и не приносится извне**: это часть поставки самого NAV, на сервере она уже лежит в
`Service\Add-ins\NavEtwReceiver`. При установке она **копируется с этого же сервера** в
подпапку `Add-ins\LineProfiler` рядом с приёмником — только потому, что NAV не
просматривает соседние папки надстроек и каждая обязана быть самодостаточной. Такое
копирование в пределах машины, где файл уже лицензирован в составе платформы,
распространением не является; в репозитории чужих двоичных файлов нет ни одного.
Происхождение и лицензия сторонней библиотеки разобраны в `THIRD-PARTY-NOTICES.md` в
корне репозитория. Экземпляры TraceEvent в других подпапках `Add-ins` (в том числе
используемые другими инструментами) не заменяются и не трогаются.

Версия TraceEvent на конкретном сервере бывает разной, а ссылка на неё в приёмнике
строгоименная — против другой версии готовая сборка не разрешится. Поэтому путей два.
Основной — собрать приёмник из исходника прямо на сервере против той библиотеки, что
там лежит: точная привязка версии получается по построению (раздел 10.1). Запасной —
взять из `dist/` готовый вариант, собранный против версии сервера: исходник
компилируется **без единой правки** против TraceEvent 1.0.11, 1.0.26, 1.0.39 и 2.0.64
(используемая часть API одинакова во всём диапазоне), и варианты под все четыре версии
выложены (раздел 10.2).

Установка меняет на сервере три вещи: появляется подпапка в `Add-ins`; в базе появляются
17 объектов; служба NAV перезапускается один раз (запущенная служба держит файлы
`Add-ins`). Кроме того, в конфигурации инстанции NAV должен быть включён параметр
`EnableFullALFunctionTracing` — без него сервер не шлёт события уровня оператора и
замер выходит пустым. Пакет установки этот параметр **не меняет**, только показывает его
текущее значение (`onsite/01-Get-Environment.ps1`); включение — осознанное действие
администратора.

## 2. Минимум контекста: NAV, C/AL, ETW

**NAV** — ERP-система; её сервер приложений (служба Windows, NST) исполняет бизнес-логику
на языке C/AL. Объекты C/AL — таблицы, страницы, отчёты, кодовые модули — живут не на
диске, а в базе данных SQL Server и ставятся штатным импортом текстового экспорта.
C/AL умеет создавать .NET-объекты из сборок, лежащих в папке `Add-ins` службы, — именно
так приёмник оказывается внутри процесса NST.

**ETW** (Event Tracing for Windows) — системная шина событий Windows: программа-провайдер
объявляет события, потребитель заводит сессию трассировки и подписывается. Сервер NAV —
зарегистрированный ETW-провайдер `Microsoft-DynamicsNAV-Server`; пока ни одна сессия не
включила его события, они не генерируются и ничего не стоят. Заведение сессии ETW —
привилегированная операция (раздел 7).

Схема работы замера: страница NAV → кодовый модуль C/AL включает штатный журнал покрытия
кода (какие строки выполнялись и сколько раз) и создаёт через приёмник сессию ETW
(сколько миллисекунд заняла каждая строка и какие запросы SQL она отправила) → по
окончании приёмник отдаёт в C/AL готовые агрегированные строки, и они склеиваются с
листингом.

## 3. Зачем своя сборка — почему не хватает штатных средств

Штатная сборка платформы `Microsoft.Dynamics.Nav.EtwListener` отдаёт в C/AL только один
приёмник — `NavPermissionEventReceiver`, события проверки прав: ни номера строки, ни
имени функции в его данных нет. Приёмник здесь повторяет приём самой Microsoft из
штатного Codeunit 9800 («ETW listener» для событий прав): объект живёт внутри процесса
NST, слушает ETW и отдаёт результат в C/AL.

Отличие — в объёме. Событие оператора C/AL приходит на **каждый выполненный оператор**:
в живом прогоне это порядка 167 тысяч событий за 80 секунд. Отдавать их в C/AL поштучно
нельзя (в том же Codeunit 9800 Microsoft прямо предупреждает не открывать транзакций в
обработчике события), поэтому агрегация идёт в .NET-сборке, а в C/AL уходят готовые
строки — их сотни. Это и есть единственная причина существования `AlLineProfiler.dll`.
Всё это написано в шапке `src/AlLineProfiler.cs`.

## 4. Что делает приёмник (`src/AlLineProfiler.cs`)

Приёмник — один публичный класс `LineProfiler.AlLineProfilerReceiver`, создаётся и
управляется только из C/AL (других точек входа у сборки нет).

**Сессия ETW.** `Start()` создаёт сессию с именем `AlLineProfiler-<PID процесса>`
с опцией `Create` (никогда не присоединяется к чужой сессии), ставит `StopOnDispose`
(сессия не переживёт процесс) и включает единственный провайдер:

| Параметр | Значение |
|---|---|
| Провайдер | `Microsoft-DynamicsNAV-Server` |
| GUID | `85423fd1-c021-5a63-f214-c4819f8809f3` (неизменен с NAV 2013) |
| Уровень | Informational |
| Маска событий (keywords) | `0xA` = `ALFunctionCallTracing` (0x8) + `SqlTracing` (0x2) |

События других провайдеров, даже если попадут в поток, отбрасываются на входе
(`OnEvent` сверяет `ProviderGuid`). При старте гасятся только собственные сессии,
оставшиеся от прежних запусков (аварийное завершение процесса), — исключительно по
приставке имени `AlLineProfiler-` (`KillStaleSessions`); чужие сессии не трогаются.

**Какие события читаются.** Род события определяется по составу полей, не по номеру:

| Род | Признак | Читаемые поля |
|---|---|---|
| Оператор C/AL | есть `lineNumber` и `functionName` | `objectType`, `objectId`, `functionName`, `lineNumber`, `statement` (текст оператора — один раз на строку) |
| Вход / выход / обрыв функции | есть `functionName` без `lineNumber` | `objectType`, `objectId`, `functionName` |
| Операция SQL (начало/конец) | есть `sqlStatement`, либо парные Start/Stop без полей кода (COMMIT и т.п.) | `sqlStatement` |

У всех событий дополнительно читается `sessionId` — для отбора по сессии NAV. Другие
поля событий (провайдер шлёт и имя пользователя сессии, и прочее) приёмник не читает и
не хранит; его диагностический каталог событий сохраняет только **имена** полей, не
значения — это отдельно оговорено комментарием в `ClassifyCached`.

**Агрегация.** В памяти держатся три структуры: статистика по строкам кода (время,
выполнения, время SQL), различные тексты запросов по строкам (одинаковый текст с одной
строки — одна запись со счётчиком) и рёбра вызовов «строка → вызванная функция». Все
три ограничены настраиваемыми пределами (раздел 9). По остановке C/AL забирает строки
через свойства-курсоры (`SelectRow` / `CurrentTotalMs` и т.п.).

**Разбор сохранённого файла.** `ProcessEtlFile(path)` прогоняет ранее записанный файл
трассировки `.etl` через тот же обработчик — для стендовой проверки агрегатора и для
сред, где класть сборку в службу не разрешили (трассу тогда пишет штатный `logman`).
Это единственное место, где приёмник касается файловой системы, и оба обращения —
чтение: `File.Exists` и чтение файла библиотекой TraceEvent.

## 5. Чего приёмник не делает — и чем это проверяется

Полный список `using` исходника: `System`, `System.Collections.Generic`,
`System.Reflection` (нужен только атрибутам сборки `AssemblyTitle`/`AssemblyVersion`),
`System.Text` (в коде не используется), `System.Threading`,
`Microsoft.Diagnostics.Tracing`, `Microsoft.Diagnostics.Tracing.Session`.

| Утверждение | Как проверить за пять минут |
|---|---|
| Не выходит в сеть | в `using` нет ни `System.Net`, ни WCF; `findstr /i "socket http webrequest tcp" src\AlLineProfiler.cs` — пусто |
| Не читает и не пишет реестр | нет `Microsoft.Win32`; `findstr /i "registry" ...` — пусто |
| Не запускает процессов | `Process.Start` отсутствует; единственное обращение к `System.Diagnostics.Process` — `GetCurrentProcess().Id` для имени собственной сессии ETW (метод `Start`) |
| Нет P/Invoke | `findstr /i "dllimport extern" ...` — пусто; системные вызовы ETW делает библиотека Microsoft TraceEvent |
| Не пишет на диск | обращения к файловой системе — только в `ProcessEtlFile`, оба на чтение (`System.IO.File.Exists` + чтение `.etl`) |
| Не обращается к базе данных | нет ни `System.Data`, ни строк подключения; у сборки в принципе нет доступа к бизнес-данным — она видит только события ETW |
| Один публичный тип | `findstr "public" src\AlLineProfiler.cs` — единственный публичный класс `AlLineProfilerReceiver`, остальные типы `internal` |
| Чужие сессии ETW не трогаются | сессия создаётся с `TraceEventSessionOptions.Create`; гасятся только имена с приставкой `AlLineProfiler-` (`KillStaleSessions`) |

## 6. Что делают объекты NAV

Объекты 110200–110207 — обычный C/AL, читается в `LineProfiler.txt`. По действиям:

**Журнал покрытия.** Кодовый модуль 110200 включает и выключает штатный платформенный
журнал покрытия (`CODECOVERAGELOG`) на время замера и читает виртуальную таблицу
2000000049 Code Coverage — листинг и счётчики выполнений даёт сама платформа. Перед
замером журнал очищается (это очистка платформенного буфера в памяти, не данных).
На случай оборванного прогона есть кнопка аварийного выключения журнала.

**Чтение метаданных платформы.** Таблица 2000000001 Object (имена и даты компиляции
объектов — чтобы пометить, с какого кода снят замер), 2000000041 Field (имена и типы
полей — для типов параметров в готовом скрипте SSMS и для советника по ключам),
2000000110 Active Session (список сессий для выбора и имя базы данных), ключи таблиц —
через штатный `RecordRef.KEYINDEX`. Всё это чтение метаданных, не бизнес-данных.

**Запись — только в свои таблицы.** Настройка, сохранённые замеры и демонстрационные
данные живут в собственных таблицах 110200–110207. Ни одна чужая таблица не пишется;
демонстрационный отчёт 110200 генерирует нагрузку исключительно на своих двух
демо-таблицах.

**Файлы.** Обкатка (self-test, по умолчанию выключена галкой настройки) пишет один
текстовый отчёт `selftest.tsv` в рабочий каталог из настройки (по умолчанию
`C:\ProgramData\LineProfiler\`) — от имени учётной записи службы. Функция разбора `.etl`
читает указанный файл с диска сервера. Страница запросов SQL умеет отдать готовый
скрипт пользователю: копией в буфер обмена **его** машины (штатный вызов на стороне
клиента, только Windows-клиент, запись в буфер без чтения) или выгрузкой файла `.sql`
штатным `DOWNLOADFROMSTREAM`. На сервере страницы не пишут ничего.

**Прямые подключения к SQL Server.** Ровно одно и только за настройкой — необязательный
съём значений параметров запросов (раздел 8). Больше объекты к базе напрямую не ходят:
вся остальная работа — штатные средства платформы.

**Запасные объекты доставки** (`onsite/Installer.template.txt`,
`onsite/Unpacker.template.txt`) — для контуров, куда нельзя копировать файлы и где не
разрешён PowerShell. Распаковщик поднимает присланные почтой base64-части со станции
пользователя (штатный `UPLOAD`), склеивает архив во временном каталоге NAV-сервера и
сразу отдаёт его обратно пользователю (`DOWNLOAD`), подчищая временные файлы. Имя
собранному файлу даёт сама рассылка — отдельной строкой `#NAME`, — и оно принимается,
только если это уже готовое имя файла: латиница, цифры, точка, дефис, пробел, не длиннее
80 знаков. Имя с разделителем пути, двоеточием или чем угодно вне этого набора не чинится
обрезкой, а отбрасывается целиком, и файл получает имя по содержимому; записать что-либо
мимо своего временного каталога объект так не может. Без клиента (headless) он читает
файлы из подкаталога `unpack` внутри собственного `TEMPORARYPATH` и ниоткуда больше:
зашитых путей в нём нет. Установщик
несёт сборку приёмника внутри себя как base64, пишет её в `Add-ins` силами службы (что
удаётся только при службе от LocalSystem — иначе честно сообщает и отдаёт файл
пользователю для передачи администратору) и умеет выдать пользователю обе сборки для
сверки. Оба объекта — такой же читаемый C/AL, как и остальные.

## 7. Права: что нужно и что будет, если прав нет

| Что нужно | Кому | Зачем | Если нет |
|---|---|---|---|
| Право создавать сессию ETW: LocalSystem, либо членство в группе Performance Log Users (SID `S-1-5-32-559`) | учётной записи службы NAV | сессию ETW заводит процесс службы, а не пользователь, нажавший кнопку | `Start()` падает с исключением либо событий нет; замер прерывается явной ошибкой с указанием причины (текст `NoTraceErr` в CU 110200) |
| `EnableFullALFunctionTracing=true` в `CustomSettings.config` инстанции | инстанции NAV (включает администратор) | без него события операторов не шлются вовсе | замер пуст; инструмент говорит об этом той же явной ошибкой |
| Запись в `Service\Add-ins` | администратору, на время установки | выложить сборку (папка платформы, штатно доступна на запись SYSTEM и администраторам) | установка невозможна |
| Перезапуск службы NAV | администратору, при установке и снятии | служба держит файлы `Add-ins` | новая сборка не подхватится |
| Запись в рабочий каталог (`C:\ProgramData\LineProfiler\` по умолчанию) | учётной записи службы | только отчёт обкатки | обкатка не выложит файл; на замеры не влияет |
| `ALTER ANY EVENT SESSION` + `VIEW SERVER STATE` на SQL Server | учётной записи службы NAV | только необязательный съём значений параметров (раздел 8) | функция сообщает об отказе в строке состояния, замер продолжается без значений |
| Разрешения NAV на объекты 110200–110207 | пользователям профайлера | штатное разграничение доступа NAV | пользователь без разрешений инструмента не видит |

Проверка прав ничего не меняет: `onsite/01-Get-Environment.ps1` показывает учётку службы
и её членство в группе, `onsite/06-Check-Sql.ps1` — права на SQL Server (и печатает
`GRANT`-команды, но не выполняет их).

## 8. Какие данные попадают в замер

Это главный раздел: профайлер по определению смотрит на работу системы, и надо точно
назвать, **что** он видит, **где** это оказывается и **сколько** живёт.

### 8.1. Что попадает всегда

- **Исходный код C/AL** профилируемых объектов — листинг строк с временем. При
  сохранении замера листинг целиком ложится в таблицы профайлера в базе NAV.
- **Тексты запросов SQL** в том виде, в каком их отправляет платформа NAV, — то есть
  **параметризованные**: `SELECT ... WHERE ("Field"=@0)`. Это структура запроса, имена
  таблиц и полей. Значений в этих текстах нет — вместо них метки `@0, @1`. Длина текста
  ограничена настройкой (8000 знаков по умолчанию).
- Номер сессии NAV, имя компании и идентификатор пользователя, **сохранившего** замер.

Не попадает: имена пользователей измеряемых сессий (события ETW их несут, приёмник эти
поля не читает — раздел 4) и значения параметров запросов, пока не включена возможность
из п. 8.3.

### 8.2. Замер чужих сессий

У замера три области: своя сессия, указанная сессия, все сессии инстанции. В двух
последних пользователь профайлера видит, **какой код и какие запросы (по структуре)
выполняют сессии других пользователей**. Это законная задача инструмента — искать, кто
грузит сервер, — но по сути это наблюдение за работой других, и доступ к нему должен
быть управляем. Управление штатное: разрешения NAV на объекты профайлера. Рекомендация —
выдавать их только тем, кто занимается производительностью, и не включать в общие роли.
Число сессий, попавших в замер, инструмент показывает в строке здоровья замера — скрыть
факт многосессионного замера нельзя.

### 8.3. Необязательный съём значений параметров — единственное место, где в замер попадают данные из базы

Платформа NAV значений параметров не отдаёт нигде (проверено по составу полей всех
событий провайдера — комментарий в `ParamStart`, CU 110200). Поэтому они снимаются на
стороне SQL Server сеансом расширенных событий (Extended Events) — и только если это
явно включено.

**Как включается.** Галка «Снимать значения параметров SQL» в настройке профайлера —
**по умолчанию выключена** (поле `Capture SQL Params` таблицы 110204 без `InitValue`),
плюс имя сервера SQL в той же настройке, плюс права из раздела 7. Без любой из трёх
составляющих замер молча идёт без значений.

**Как устроено.** На время замера кодовый модуль создаёт на SQL Server сеанс событий
`AlProfiler_<номер сессии NAV>` из двух событий — `sqlserver.rpc_completed` (несёт
значения) и `sqlserver.sp_statement_completed` (несёт текст оператора), — отфильтрованных
**по имени базы данных этой инстанции NAV**. Приёмником служит кольцевой буфер в памяти
SQL Server, ограниченный 16 МБ. По окончании замера буфер вычитывается одним запросом к
`sys.dm_xe_session_targets`, и сеанс **безусловно удаляется** — даже если чтение не
удалось (`ParamStop`). Подключение — `System.Data.SqlClient` с `Trusted_Connection`, то
есть под учётной записью службы NAV, без каких-либо сохранённых паролей. Это единственное
сетевое взаимодействие инструмента, и идёт оно к собственному серверу базы данных.

**Что это за данные и где они оказываются.** Значения параметров — это **фактические
данные из строк базы**: при включённой возможности в замер могут попасть персональные и
коммерческие данные, которыми оперировал профилируемый код. Живут они так:

- во время замера — в памяти сессии NAV (временные записи);
- при **сохранении** замера — переносятся в таблицу 110205 базы NAV (BLOB-поле
  «Значения параметров») и живут там **до удаления замера** пользователем; вместе с
  базой попадают и в её резервные копии;
- видит их каждый, у кого есть разрешения NAV на таблицы и страницы профайлера;
- наружу инструмент их не отправляет; выгрузить их может пользователь — тем же скриптом
  `.sql`, что и текст запроса (буфер обмена / файл на его станции).

**Рекомендация.** Держать возможность выключенной (как по умолчанию) и включать точечно
под конкретный разбор; сохранённые замеры со снятыми значениями рассматривать как
выгрузку данных: удалять после анализа, доступ к таблицам профайлера не раздавать
широко. Права `ALTER ANY EVENT SESSION`/`VIEW SERVER STATE` можно не выдавать вовсе —
тогда возможность недоступна технически, что бы ни стояло в настройке.

**Аварийный случай.** Если процесс NAV упал между стартом и остановкой замера, сеанс
событий останется на SQL Server до ручного удаления (перезапуск SQL Server его тоже
снимает). Проверка и уборка:

```sql
SELECT name FROM sys.server_event_sessions WHERE name LIKE 'AlProfiler_%';
DROP EVENT SESSION [AlProfiler_<номер>] ON SERVER;
```

## 9. Влияние на работу системы

**Трассировка живёт только внутри замера.** Кнопка «Старт» включает журнал покрытия и
сессию ETW, кнопка «Стоп» выключает; вне этого окна провайдер никем не включён и событий
не генерирует — это свойство ETW, а не обещание инструмента. Сессия создаётся с
`StopOnDispose`, а на старте убираются свои же сессии, осевшие после аварийного
завершения. Если процесс службы был убит жёстко, осиротевшую сессию можно увидеть и
снять вручную: `logman query -ets` → `logman stop AlLineProfiler-<PID> -ets`.

**Порядок величин.** Живой прогон на демонстрационном отчёте — около 167 тысяч событий
за 80 секунд (~2 тысячи в секунду). От захлёбывания сервер защищают, по коду приёмника:

- разбор идёт в одном фоновом потоке (`IsBackground` — остановку службы не держит);
- род события определяется один раз на номер события и кэшируется (`ClassifyCached`);
- строковые поля читаются скупо: текст оператора берётся один раз на строку кода
  (`_haveText`), текст запроса — только у внешней операции SQL;
- память ограничена жёсткими пределами с настройкой: различных текстов запросов —
  2000 (потолок 20000), длина текста — 8000 знаков (потолок 30000), рёбер вызова —
  5000 (потолок 50000), глубина стека кадров — 512; всё, что сверх предела, считается
  и честно показывается как отброшенное;
- ожидания ограничены: добор хвоста событий — 8 с по умолчанию, дожидание разбора
  очереди при остановке — жёсткий потолок 120 с (`JoinWhileParsing`).

**Журнал покрытия** в многосессионных областях ведётся по всей инстанции (у платформы
нет пожаночного включения) — это и есть основная накладная стоимость окна замера.
Замер — операция диагностическая: запускать его на нагруженной инстанции стоит осознанно
и на ограниченное время, как любой профайлер.

**Сеанс расширенных событий** (если включён): кольцевой буфер не больше 16 МБ в памяти
SQL Server, задержка рассылки 1 с, режим `ALLOW_SINGLE_EVENT_LOSS`; после замера сеанс
удаляется.

**Установка и снятие** — единственные моменты, когда перезапускается служба NAV, то есть
плановая краткая недоступность инстанции.

## 10. Как проверить самостоятельно

Проверка многослойная; слои независимы.

### 10.1. Главный путь: собрать из исходника на целевом сервере

Основной путь установки вообще не требует доверять двоичному файлу из репозитория:
`onsite/03-Build-Receiver.ps1` собирает приёмник **на месте** штатным компилятором из
состава .NET Framework — `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`
(версия файла 4.8.9221.0). Сборка — один вызов:

```
csc /nologo /target:library /optimize+ /out:AlLineProfiler.dll ^
    /reference:<путь к Microsoft.Diagnostics.Tracing.TraceEvent.dll на этом сервере> ^
    src\AlLineProfiler.cs
```

Один исходный файл, одна ссылка на сборку, уже лежащую на сервере. Никаких NuGet,
пакетных менеджеров и обращений в сеть при сборке нет — это видно из самого шага 03
(один вызов `csc`, весь скрипт — 69 строк). Проверяющий читает `src/AlLineProfiler.cs`
(разделы 4–5 выше — конспект того, что он там увидит) и получает сборку собственной
машиной.

### 10.2. Если ставится готовая сборка из `dist/`

В `dist/` лежат пять сборок, и все пять — наши, собранные из одного и того же
`src/AlLineProfiler.cs`: основная сборка `AlLineProfiler.dll` (против TraceEvent
1.0.39) и четыре варианта в `dist/variants/` — против TraceEvent 1.0.11, 1.0.26,
1.0.39 и 2.0.64 (назначение файлов — `dist/README.md`). Выбирается вариант под ту
версию TraceEvent, что уже лежит на сервере (версию печатает
`onsite/01-Get-Environment.ps1`; команда для ручной проверки — в 10.3). Канонический
источник хешей — `dist/SHA256SUMS.txt`, там суммы всех пяти сборок. На момент этой
редакции основная сборка:

| Файл | Размер, байт | SHA-256 |
|---|---|---|
| `dist/AlLineProfiler.dll` | 29 184 | `a0186f38ff5709ed02900110f4ca6d1c019d450e09ea4d73dc3df6fd32c27eba` |

Степень проверки вариантов — честно: **компиляцией** без единой правки исходника
проверены все четыре версии TraceEvent; **прогоном** проверена только сборка против
1.0.39 — встроенной обкаткой на стенде NAV 2018, «пройдено 55 из 55». Сервера с другой
версией TraceEvent под рукой не было, поэтому вариантные сборки следует считать
проверенными на компиляцию, но не на прогон; при малейшем сомнении — путь 10.1, он от
версии библиотеки не зависит по построению.

Честная оговорка: **побайтно воспроизвести `AlLineProfiler.dll` пересборкой нельзя.**
У `csc` 4.8.9221.0 нет ключа детерминированной сборки, и компилятор штампует в файл
новые отметку времени и GUID модуля на каждом прогоне. Проверить это можно за минуту:
собрать сборку дважды и сравнить (`fc /b a.dll b.dll`). Ожидаемый результат — файлы
одинакового размера, различающихся байтов **21 из 29 184**, все в служебных полях,
ни одного в коде:

- 1 байт по смещению `0x000088` — поле TimeDateStamp заголовка PE;
- 16 байт подряд `0x00639C..0x0063AB` — GUID модуля (MVID) в метаданных;
- по 1 байту в `0x004655`, `0x005B20`, `0x006DEE`, `0x006E52` — производные от отметки
  времени и контрольной суммы.

Той же процедурой сверяется и сборка из `dist/` против собственной: та же картина
расхождений — значит код идентичен исходнику. Опубликованный хеш закрепляет конкретный
присланный артефакт, не более того; для полного недоверия к нему есть путь 10.1.

### 10.3. TraceEvent: убедиться, что на сервер не принесено ничего чужого

`Microsoft.Diagnostics.Tracing.TraceEvent.dll` — сторонняя сборка Microsoft из поставки
самого NAV. Инструмент её не приносит вовсе: при сборке на месте (10.1) серверный
экземпляр используется как есть, при установке готового варианта серверный экземпляр
копируется в `Add-ins\LineProfiler` (раздел 1). Проверка — две команды на самом сервере:

```powershell
$f = '<корень NAV>\Service\Add-ins\NavEtwReceiver\Microsoft.Diagnostics.Tracing.TraceEvent.dll'
[Reflection.AssemblyName]::GetAssemblyName($f).FullName
(Get-Item $f).VersionInfo | Format-List ProductName,CompanyName,LegalCopyright,FileVersion
Get-FileHash $f -Algorithm SHA256
```

Ожидаемая идентичность: строгое имя с токеном ключа Microsoft `b03f5f7f11d50a3a`;
метаданные файла — ProductName `Microsoft.Diagnostics.Tracing.TraceEvent`, Company
`Microsoft Corporation`; версия зависит от сборки платформы (в поставке NAV 2018 —
1.0.39.0). После установки хеш копии в `Add-ins\LineProfiler` должен побайтно совпадать
с хешем файла в `NavEtwReceiver` на этом же сервере — это и есть проверка «ничего
чужого не принесено». Происхождение библиотеки, история смены её лицензии и побайтное
совпадение поставочного файла NAV с публичным пакетом NuGet — в
`THIRD-PARTY-NOTICES.md`; здесь этот разбор не дублируется.

### 10.4. Объекты NAV

`LineProfiler.txt` — простой текст, никакой упаковки: каждый объект читается целиком.
После импорта состав в базе сверяется запросом (его же печатает шаг
`onsite/04-Import-Objects.ps1`):

```sql
SELECT Type, ID, Name, Compiled FROM dbo.[Object]
WHERE ID BETWEEN 110200 AND 110207 AND Type IN (1,3,5,8) ORDER BY Type, ID;
```

Должно быть ровно 16 строк, все `Compiled = 1`, все имена с приставкой профайлера.

## 11. Как снять

1. Если замер был оборван — открыть страницу профайлера и нажать аварийное выключение
   журнала покрытия (иначе платформенный флаг журнала переживёт удаление объектов).
2. Удалить объекты 110200–110207 в среде разработки NAV (C/SIDE, выделить → Delete, с
   синхронизацией схемы). Вместе с таблицами из базы уходят **все** сохранённые замеры,
   настройка и демо-данные — отдельной чистки не требуется.
3. Удалить каталог `Service\Add-ins\LineProfiler` и перезапустить службу NAV.
4. Если для инструмента включали `EnableFullALFunctionTracing` — решить, возвращать ли
   его назад (это параметр платформы, не инструмента).
5. Проверить хвосты аварийных сценариев: сессии ETW `AlLineProfiler-*`
   (`logman query -ets`), сеансы `AlProfiler_%` на SQL Server (запрос в п. 8.3),
   файлы в рабочем каталоге (`selftest.tsv`) и временную папку сборки
   `%TEMP%\LineProfiler-build` на машине, где запускался шаг 03.

После этого от инструмента не остаётся ничего: записей в реестре, служб, планировщика
и правок конфигурации он не делает (единственная правка конфигурации — п. 4 — делается
администратором руками и им же решается).
