# LineProfiler — построчный профайлер C/AL

Инструмент для Microsoft Dynamics NAV. Разработка ведётся на **NAV 2018** (платформа 11.x),
целевая среда установки — **тот же NAV 2018** в изолированном контуре. Интерфейс — страница NAV по
образцу штатной `Page 9990 Code Coverage`; листинг и число выполнений даёт платформа через
виртуальную `Table 2000000049 Code Coverage`, время — свой приёмник ETW на C# внутри процесса
службы; склейка по «тип объекта + код объекта + номер строки».

## Репозиторий ПУБЛИЧНЫЙ — что сюда нельзя

Он открыт и служит материалом для согласования установки службой безопасности. Поэтому:

- **Никаких упоминаний конкретной установки**: имён баз данных, названий компаний и их
  систем, номеров и имён доработанных объектов заказчика, номеров задач трекера. Если нужен
  пример объекта — брать штатный NAV (`Codeunit 80 Sales-Post`, `Table 37 Sales Line`).
- **Никаких чужих двоичных файлов.** `TraceEvent` берётся с целевого сервера — почему именно
  так, разобрано в [THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md), и это не вкусовщина, а
  лицензионный запрет.
- **Никаких следов ИИ** ни в коде, ни в комментариях, ни в сообщениях коммитов: ни имён
  ассистентов, ни «generated by», ни атрибуции. Комментарии пишутся как заметки разработчика.
- Секреты и пароли — только вне репозитория.

Имя базы для стенда берётся из переменной окружения `LP_DATABASE`, путь к выгрузке объектов
целевой базы — из `LP_BASELINE_DIR`. Захардкоженных имён в коде быть не должно.

## Платформа (строго)

Только C/SIDE и язык **C/AL**. Никакого AL, никаких расширений AppSource, никакого BC13+.
Типы объектов — только те, что NAV 2018 поддерживает: Table, Page, Report, Codeunit, XMLport,
Query, MenuSuite. Не Form (удалена в 2013) и не Dataport (тоже). Отчёты — RDLC или Word layout.

Компиляция в порядке зависимостей: Table → Codeunit → Report → Page.

Приёмник — C# под .NET Framework, компилятор `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`.
Он **дорослиновский** и понимает только C# 5: без интерполяции строк, без `?.`, без `nameof`.

## Кодировки — здесь ломается чаще всего

| Что | Как |
|-----|-----|
| `LineProfiler.txt` (объекты C/SIDE) | UTF-8 **без BOM**, переводы строк **CRLF** |
| `.ps1` для Windows PowerShell 5.1 (`onsite/`) | UTF-8 **С BOM**, CRLF |
| `.ps1` под pwsh 7 (`#requires -Version 7`) | UTF-8 без BOM, CRLF |
| Шаблоны объектов `onsite/*.template.txt` | **только латиница**, они едут телом письма |
| Импорт в C/SIDE | cp866 (`scripts/convert-for-cside.ps1`), cp1251 и UTF-8 ломают кириллицу |
| `dist/SHA256SUMS.txt` | **LF**, иначе `sha256sum -c` принимает возврат каретки за часть имени |

Windows PowerShell 5.1 читает файл **без BOM как ANSI** и ломается на кириллице в кавычках:
часть команд печатается вместо выполнения. Это не теория — ловилось несколько раз.
`.gitattributes` держит переводы строк у любого, кто склонирует; менять его осторожно.

## Соглашение о комментариях

Тег изменения — `DD <ДД.ММ.ГГГГ> LineProfiler`, четырёхзначный год. Одна строка — тег в конце
через один пробел; несколько — парные маркеры `>>` … `<<`. В `OBJECT-PROPERTIES` при правке:
`Date=` (формат `ДД.ММ.ГГ`, **дву**значный год), `Time=`, `Modified=Yes`. Форматы дат не путать.
Documentation-блок (`BEGIN { … } END.`) пополняется одной строкой с кратким описанием правки.

Ловушки C/SIDE: тег `>>` ставится после `BEGIN`, а **не в блоке VAR** — там комментарии
запрещены; в `ActionList` и `Controls` комментариев `//` нет вовсе, импорт падает с
«A '{' (ElemBegin) is expected»; `TextConst` ломается на внутреннем `=`.

## Как проверять — прогоном, а не рассуждением

1. `pwsh scripts/Test-ObjectFile.ps1 LineProfiler.txt` — оформление, кодировка, парность
   тегов, а заодно согласованность с `LineProfiler.fob`: состав объектов по оглавлению
   контейнера и происхождение по `fob-origin.txt`. **Эталон: 0 ошибок.**
2. `scripts/Test-AlTrace.ps1` — ядро разбора трассировки на коротких потоках событий,
   где верный ответ посчитан руками, плюс сборка отчёта по готовому HTML.
   **Эталон: 86 из 86.** Идёт и под 5.1, и под pwsh 7,
   не требует ни базы, ни трассировки, ни дампа — гонять после любой правки
   `Lib-AlTrace.ps1` или `Build-Report.ps1`.
3. `scripts/Test-KeyAdvisor.ps1` — советник по ключам. Корпус Г (разбор WHERE) и
   корпус Д (покрытие ключами на синтетическом справочнике из трёх строк) идут на
   чистой копии и судят сами: **эталон — 89 из 89**. Корпуса А, Б и В опираются на
   справочники из `LP_BASELINE_DIR` и без них пропускаются, не роняя прогон.
4. `scripts/Test-PerfLint.ps1` — правила линтера на синтетическом объекте: дамп
   исходников и текстовый экспорт для символов собираются прямо в прогоне, ни базы,
   ни выгрузки не нужно. **Эталон: 21 из 21.**
5. `powershell scripts/Test-Unpacker.ps1 -Import` — распаковщик base64 (`Codeunit 110207`)
   на стенде, без клиента: собранный файл сличается по сумме с исходным, а имя из
   рассылки — с тем, под каким он лёг. **Эталон: 46 из 46.**
   Единственная проверка, которой нужна база: объект C/AL снаружи NAV не исполняется.
6. `pwsh scripts/Deploy-LineProfiler.ps1` — сборка приёмника и выкладка на стенд.
7. Встроенная обкатка: включить `Self Test Enabled` в настройке и запустить `Codeunit 110200`
   (headless — `Invoke-NAVCodeunit`, **только под Windows PowerShell 5.1**, pwsh 7 модуль не грузит).
   Результат — `selftest.tsv` в рабочем каталоге, первая строка «passed N of M».
   **Эталон: 32 из 32.** Любое расхождение разбирать до конца.
8. Перед отправкой на объект — собрать пакет и поставить из него, а не из рабочей копии.

Обкатка обязана **судить сама**: «пройдено N из M» первой строкой, и первая проверка — что
результат вообще не пуст, иначе остальные проходят вхолостую.

## Факты, которые дорого достались

- **TraceEvent строгоименная**: сборка против 1.0.39 против 1.0.11 не свяжется. Но исходник
  приёмника собирается **без единой правки** против 1.0.11, 1.0.26, 1.0.39 и 2.0.64 — поэтому
  приёмник собирают **на целевом сервере** против того, что там лежит.
- **Лицензия TraceEvent сменилась на MIT только с 2.0.31** (12.12.2018). Версии из поставки NAV
  старше и распространяться не могут. Старая ссылка на лицензию сегодня редиректит на страницу
  со словом MIT — это ловушка, лицензия лежит внутри пакета NuGet.
- **`csc` не знает `/deterministic`**: две сборки одного исходника различаются 21 байтом из
  29 184 (GUID модуля и отметки времени). Обещать сверку хешей пересборкой нельзя.
- **Служба отпускает файл не сразу**: `Stop-Service` вернулся ≠ файл свободен. Ждать
  освобождения самого файла, иначе копирование падает «used by another process».
- **В Windows PowerShell 5.1 у одиночного объекта нет свойства `Count`** — `$x.Count` даёт
  `$null`, и проверки вида `if ($x.Count)` молча не срабатывают. Оборачивать в `@()`.
- **`Flush()` живой сессии ETW глушит доставку**: замер выходит пустым, но выглядит удачным —
  ни ошибок, ни потерь, просто ноль. Хвост дожидаться, а не сбрасывать.
- **Журнал покрытия гасить ДО остановки приёмника**: окно покрытия обязано лежать внутри окна ETW.
- **Смещение номера строки не константа**: трассировка даёт ОПЕРАТОР, листинг — СТРОКУ целиком,
  поэтому сверка идёт по началу строки, а не по равенству. Единственный отказ, который выглядит
  как успех, — снимать его перед каждой сборкой.
- **Правку настройки мимо NAV сервер не видит**: при работающей службе строка
  `AL Profiler Setup` лежит в кэше, и `UPDATE` прямо в SQL до сессии не доходит.
  `Codeunit 110200` при этом отрабатывает мгновенно и молча — `RunSelfTestIfAsked`
  выходит по невзведённой галке, `selftest.tsv` не появляется. Диагноз «нет прав на
  запись», который печатает `onsite/05-Invoke-SelfTest.ps1`, в этом случае ложный.
  Лечится сбросом кэша — перезапуском экземпляра службы.
- **`.fob` и `.txt` расходятся молча, и по самому контейнеру этого не видно.** В начале
  `.fob` лежит оглавление открытым текстом — тип, номер, имя, дата, время, размер, список
  версий, — но `Date=` в `OBJECT-PROPERTIES` ставится руками, а время у нас всегда
  `12:00:00`: правка кода в тот же день оглавление не меняет вовсе. Ловилось вживую —
  контейнер отставал от текста на восемь коммитов при полностью совпавшем составе.
  Собрать `.fob` из `.txt` скриптом нельзя, это делает C/SIDE, поэтому происхождение
  ОБЪЯВЛЯЕТСЯ в `fob-origin.txt` (хэш текста на момент выгрузки) и сверяется прогоном.
  Обновлять манифест без перевыгрузки — превращать проверку в ложь; `Update-FobOrigin.ps1`
  поэтому требует `-Force` именно в этом случае.
- **`ERROR` в объекте C/AL посреди чтения файла оставляет файл открытым на службе.**
  Дескриптор живёт до конца сессии, и следующий запуск встаёт на том же файле — снаружи
  это выглядит как «объект виснет на любой ошибке». Лечится не обработкой ошибки, а её
  отсутствием: `Codeunit 110207` не зовёт `ERROR` вовсе, любой отказ идёт одним путём —
  закрыть файлы, вычистить временный каталог, вывести причину. Проверка обязана включать
  случай «отказ, а сразу за ним — исправный запуск».
- **`Convert.FromBase64String` бросает исключение, и в C/AL его не поймать** (`TryFunction`
  в C/AL нет). Поэтому строка проверяется ДО раскодирования: алфавит регуляркой
  `System.Text.RegularExpressions.Regex` (она в C/AL доступна и на NAV 2018 работает) плюс
  длина, кратная четырём. Это весь контракт base64 — что его прошло, то не бросит.
- **Первый `Invoke-NAVCodeunit` после долгого простоя может не уложиться в таймаут**:
  вызов висит около полутора минут и возвращает ошибку, а следующий за ним проходит за
  полсекунды на тех же данных. Красный прогон сразу после паузы — повод повторить его на
  прогретой службе, а не искать причину в объекте.
- **`TEMPORARYPATH` у NAV — это не temp учётной записи службы**, а профиль экземпляра:
  `…\Server\<экземпляр>\users\default\<домен>\<пользователь>\TEMP`. Искать результат
  headless-прогона в `C:\Windows\Temp` бесполезно, и «файла не появилось» там ложно.
- **base64, склеенный не в том порядке, остаётся валидным base64.** Раскодируется молча и
  даёт мусор, поэтому части несут свой номер строкой `#PART nn OF mm` — латиницей, потому
  что распаковщик сплошь латинский и русскую шапку прочитать не может.
- **Имени файла в base64 нет** — там одни байты. Рассылка объявляет его строкой
  `#NAME <имя>` рядом с `#PART`, и распаковщик берёт его, только если это уже готовое имя:
  латиница, цифры, точка, дефис, пробел, до 80 знаков. Имя с путём не чинится обрезкой до
  последней части, а отвергается целиком — это единственное место, где объект уговорили бы
  записать файл мимо своего temp. Без имени файл называется по сигнатуре: `payload.zip`.
- **Зашитых путей в распаковщике нет.** С клиентом он файлы СПРАШИВАЕТ (`UPLOAD`), без
  клиента — читает всё, что лежит в `TEMPORARYPATH\unpack`, под любыми именами. Прежние
  четыре кандидата вида `C:\LineProfiler` с шаблоном `part01.txt` были вдвойне незаметны:
  диалог выбора файлов заслонял то, что объект вообще куда-то смотрит сам.
- NAV **не просматривает соседние папки надстроек**: каждая папка в `Add-ins` обязана быть
  самодостаточной. Через `Table 2000000069 Add-in` серверную сборку отдать нельзя (проверено).

## Стиль работы

- Уточняющие вопросы задавать **по одному**.
- При правке `.txt` читать и писать как UTF-8 без BOM, CRLF, не сдваивать `\r`.
- После каждого коммита — `git push origin master`; локальные коммиты не накапливать.
