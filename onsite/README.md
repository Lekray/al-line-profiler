# Пакет для установки на сервере — построчный профайлер C/AL

Всё, что нужно, чтобы поставить и проверить профайлер в изолированном контуре **за один
заход**. Обратная связь — скриншотами: каждый шаг печатает свой результат одним экраном
и начинается с метки вида `=== ЛП-01 ОКРУЖЕНИЕ ===`, чтобы снимок нельзя было спутать.

Целевая среда — **NAV 2017**, разрабатывалось на **NAV 2018**. Расхождения между ними
и ловит первая половина пакета.

## Порядок

Шаги 1 и 2 ничего не меняют. Шаги 3–5 меняют: кладут сборку в `Add-ins`, перезапускают
службу, заводят 16 объектов. Шаг 6 необязательный и тоже ничего не меняет.

**Делать всё подряд в один заход.** Если шаг упадёт — упадёт громко, и снимок экрана
скажет почему; ждать ответа перед следующим шагом не нужно.

| Шаг | Что делает | Меняет? | Что снять |
|-----|------------|---------|-----------|
| `01-Get-Environment.ps1` | платформа, служба, `TraceEvent.dll`, права на ETW | нет | весь экран |
| `02-Get-EtwManifest.ps1` | имена полей событий ETW | нет | весь экран |
| `03-Build-Receiver.ps1` | собирает приёмник **на месте**, кладёт в `Add-ins` | **да** | весь экран |
| `04-Import-Objects.ps1` | импорт + компиляция объектов, сверка по базе | **да** | весь экран |
| `05-Invoke-SelfTest.ps1` | обкатка: «пройдено N из M» | **да** | весь экран |
| `06-Check-Sql.ps1` | права на съём значений параметров | нет | весь экран |

Запускать **на самом сервере NAV**, в обычном Windows PowerShell (`powershell.exe`),
от учётки с правами администратора:

```
powershell -ExecutionPolicy Bypass -File .\01-Get-Environment.ps1
```

Если инстанций NAV несколько — добавить `-Instance <имя>` к каждому шагу.

Пакет рассчитан на **Windows PowerShell 5.1**: на сервере 2017 года PowerShell 7 может не
стоять вовсе, поэтому в скриптах нет ничего из семёрки.

## Если PowerShell на сервере запускать нельзя

Всё делается руками, только дольше:

1. **Объекты** — C/SIDE → `File → Import` → `objects\LineProfiler.cp866.txt` →
   скомпилировать **все** 16 объектов (`110200..110207`, типы Table/Report/Codeunit/Page).
   Именно **все**: импорт сбрасывает флаг `Compiled`, а на недокомпилированной таблице
   сервер отвечает «Объект метаданных Table N не найден» и в лог ничего не пишет.
2. **Приёмник** — файл `receiver\AlLineProfiler.dll` положить в
   `<корень NAV>\Service\Add-ins\LineProfiler\`, службу перезапустить. Это сборка,
   собранная у нас; если она не подойдёт по версии `TraceEvent.dll`, понадобится шаг 3.
3. **Обкатка** — открыть настройку профайлера, поставить галку «Обкатка», затем
   Object Designer → `Codeunit 110200` → `Run`. Вердикт покажется одним окном сообщения —
   его и снять. Галку потом снять обратно.

## Что именно я жду увидеть на снимках

**Шаг 1.** Версия платформы, есть ли `TraceEvent.dll` и какой версии, стоит ли
`EnableFullALFunctionTracing`, от какой учётки идёт служба.

Без `TraceEvent.dll` приёмник не соберётся. Без `EnableFullALFunctionTracing` события
операторов не шлются вовсе и замер выходит **пустым** — в NAV 2017 этот параметр требует
**перезапуска инстанции**, в отличие от 2018.

**Шаг 2.** Имена полей событий. Приёмник читает нагрузку **по именам**, а не по номерам,
поэтому разные номера событий и версии шаблонов ему безразличны — а вот другие ИМЕНА
пришлось бы править. Сверять надо с этим списком:

```
оператор  : objectType objectId functionName lineNumber statement
вход/выход: objectType objectId functionName
SQL       : sessionId sqlStatement
```

**Шаг 4.** Первая ошибка разбора C/SIDE, если она будет. Она закрывает сразу половину
открытых вопросов: приняла ли платформа 2017 наши атрибуты (`[External]`, подписки на
события) и свойства страниц (`PageType=Worksheet`, `StyleExpr`, `ShowAsTree`,
`ApplicationArea`). Проверить это заранее было нечем — в наших выгрузках NAV 2009 нет
ни одной страницы, только формы.

**Шаг 5 — самое важное.** Строка «пройдено N из M» и все `FAILED`. Отдельно смотрю строку
про **смещение номера строки**.

Это единственный отказ, который выглядит как успех: если смещение между номером строки в
трассировке и в листинге на 2017 другое, соседняя строка почти всегда существует, промахов
ноль, здоровье зелёное — а время висит **не на той строке**. Поэтому профайлер снимает
смещение фактом: трассировка несёт текст оператора, журнал покрытия — текст строки, и
совпадение текстов решает. На стенде 2018 это даёт «смещение 1, тексты сошлись 19 против 0».
Если на 2017 выйдет смещение 0 — профайлер подстроится сам и скажет об этом в строке
здоровья; если голосов не будет вовсе — тоже скажет, и вот тогда нужен разбор.

## Если пакет ехал почтой

Почтовый фильтр контура удаляет вложения, поэтому пакет умеет ехать **текстом в теле
письма**: `scripts/New-MailPackage.ps1` собирает его в base64 и режет на части.
Двоичного в почтовом варианте нет вовсе — собранная сборка приёмника не кладётся
(её всё равно полагается пересобирать на месте шагом 3), исходник в UTF-8 тоже.

```
LineProfiler-mail-00a-instructions.txt    инструкция к распаковщику (по-русски)
LineProfiler-mail-00b-unpacker-object.txt объект NAV, тело сохранять КАК ЕСТЬ
LineProfiler-mail-01..NN.txt              части пакета
```

**Путь первый — PowerShell.** Сохранить тела писем 01..NN как `part01.txt`…, затем:

```powershell
$t = Get-ChildItem part*.txt | Sort-Object Name | Get-Content
$b = -join (($t -match '^\|') -replace '^\|','')
[IO.File]::WriteAllBytes("$PWD\pkg.zip", [Convert]::FromBase64String($b))
(Get-FileHash .\pkg.zip -Algorithm SHA256).Hash
Expand-Archive .\pkg.zip -DestinationPath .\LineProfiler
```

Сумму сверить с той, что напечатана в шапке части 1.

**Путь второй — объектом NAV,** если PowerShell на сервере запускать нельзя.
`Codeunit 110207` импортируется из C/SIDE, читает те же `part*.txt` **с диска сервера**
и собирает из них `pkg.zip`; дальше архив распаковывается Проводником. Объект сплошь
латинский — он едет телом письма и сохраняется в любой кодировке, ломаться нечему.
После распаковки его можно удалить.

**Почему полезная нагрузка помечена чертой в начале строки.** Первая версия отбирала
строки по длине — и обратная сборка не сошлась: у каждой части последняя строка короче
остальных, и отбор её выбрасывал. Теперь строки короткие (65 знаков), чтобы их не
переносил никакой почтовый клиент, а отбор идёт по метке, а не по длине.

## Состав пакета

```
01..06-*.ps1          шаги, каждый печатает один экран
_Common.ps1           общее: поиск службы, корня NAV, базы (правки не требует)
objects/
  LineProfiler.cp866.txt   объекты под импорт в C/SIDE (кодировка cp866)
  LineProfiler.txt         тот же исходник в UTF-8, на случай правок на месте
receiver/
  AlLineProfiler.cs        исходник приёмника ETW
  AlLineProfiler.dll       сборка с нашего стенда (запасной вариант)
MANIFEST.txt          состав пакета с размерами и контрольными суммами
```

## Что пакет НЕ делает

- Не трогает чужой профайлер `EtwPerformanceProfiler`: наша сборка ложится в свою
  подпапку `Add-ins\LineProfiler`, чужая остаётся как есть.
- Не создаёт объектов вне диапазона `110200..110207`.
- Не меняет ни одной таблицы базы, кроме своих: настройка профайлера, сохранённые замеры.
- Не выходит в сеть.

## Откат

Обкатка и замеры живут в собственных таблицах — снести можно вместе с объектами:
C/SIDE → выделить `110200..110207` → `Delete`. Сборку — удалить каталог
`Add-ins\LineProfiler` и перезапустить службу. Журнал покрытия гасится сам, а если
остался включённым — кнопка «Аварийно выключить» на странице профайлера.
